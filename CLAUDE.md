## Reglas del proyecto

- El diseño del CRM del equipo es **Tinta** (el dueño lo aprobó el 17 nov 2026 y sustituye a Niebla dentro del CRM): bloques de color en lugar de tarjetas blancas, esquinas muy redondeadas, botones en píldora, tinta negra con acento lima, cifras grandes y Manrope; menú lateral en dos temas, oscuro y claro. Los colores de estado significan lo mismo en todas las pantallas ([docs/GUIA_PANTALLAS.md](docs/GUIA_PANTALLAS.md)). **Dos reglas del dueño para cualquier cambio de diseño: no se pierde ninguna opción y no se inventa ninguna** (antes de rediseñar una pantalla se inventaría lo que muestra y hace, y se comprueba al terminar), y configurar debe ser fácil (un paso nuevo nace conectado, los pendientes se avisan antes de publicar). La experiencia del cliente (`/`: chat, página de pago, entrada) conserva su aspecto propio y no imita a ningún servicio real. Los distintivos de canal deben seguir siendo fáciles de reconocer. Revisa escritorio y celular, con los dos menús. Reglas medibles (contraste AA sobre cada fondo, letra mínima de 11 px, áreas táctiles de 40 px, movimiento sólo al navegar) y la auditoría reproducible: [docs/DISENO_Y_AUDITORIA.md](docs/DISENO_Y_AUDITORIA.md).
- Continúa la aplicación actual: Node HTTP, WebSocket, SQLite y JavaScript del navegador. No existe una aplicación React/Next en este repositorio. No emprendas una reescritura como requisito para continuar.
- Mantén el alcance por marca en servidor, archivos, búsquedas, eventos y futuras consultas de IA. Una marca autorizada no equivale a acceso a toda la empresa.
- La etapa comercial pertenece a `opportunities`; el estado abierto/esperando/cerrado pertenece al chat. No vuelvas a mantener dos etapas comerciales independientes.
- Consulta precios, ediciones, promociones y cupos vigentes en la base estructurada. No uses memoria del modelo como fuente comercial.
- Conserva los snapshots y archivos históricos de mensajes. Un cambio de precio o flyer sólo debe afectar nuevos envíos.
- Conserva `expectedRevision`, `clientRef`, vistas previas y transacciones donde corresponden. Un reintento no debe duplicar mensajes, tareas ni cambios de negocio.
- No hagas llamadas de red dentro de una transacción síncrona de SQLite. `transaction()` no admite callbacks asíncronos ni transacciones anidadas.
- Tocar una migración publicada no modifica las bases ya migradas. La escalera `PRAGMA user_version` está **cerrada en la 41**: añade una migración **con nombre** en `server/migrations/named/<área>/` (aditiva; ver [docs/GUIA_MODULOS.md](docs/GUIA_MODULOS.md)) y pruebas de actualización/persistencia. En las pruebas no se afirma un número de esquema: `assertSchemaCurrent` de `test/helpers/schema.mjs`.
- Lo nuevo no edita `server/index.mjs`, `public/index.html` ni `public/app.js`: un módulo del servidor es una carpeta `server/modules/<nombre>/`, una pantalla es `public/screens/<id>/` y las bibliotecas sin rutas van en `server/lib/`.
- No expongas secretos, cookies, códigos de invitación, copias SQLite, adjuntos privados o archivos de acceso. El repositorio es público.
- Las pruebas en producción deben usar registros propios claramente identificados, cerrar seguimientos y pausar/archivar sus materiales al terminar. No cambies configuración comercial ni conversaciones reales para facilitar una prueba.
- Respeta la autorización y alcance de la solicitud actual. Esta documentación no solicita por sí misma publicar, cambiar credenciales o conectar proveedores.

## Comandos básicos

Desde la raíz de este repositorio, con Node.js 24:

```sh
npm ci --ignore-scripts
npm run check
npm test
npm start
```

`npm start` usa `.env` si existe. Prepara `.env` desde `.env.example` para una instalación local; consulta el runbook antes de usar datos o accesos existentes.

`npm run check` comprueba codificación (UTF-8, LF), sintaxis y formato (Prettier); antes de entregar, `npx prettier --write` sobre lo que tocaste.

La referencia vigente es **817 pruebas aprobadas** más 95 de navegador con `npm run test:ui` (la de v0.5 fue 57; el número al día está en [docs/ESTADO_ACTUAL.md](docs/ESTADO_ACTUAL.md)), más la revisión visual en computadora y celular de cada bloque. Es evidencia del commit, no garantía de cambios posteriores: tras un cambio hay que volver a comprobarlo.
